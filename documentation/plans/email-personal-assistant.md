# Email Personal Assistant — Build Plan

## Agreed context

- The inbox narrative should be followed by concrete, clickable actions generated by the digest model.
- Grouped AI mutations enter the existing pending-action review queue. Users explicitly Apply or Dismiss them; existing source/action trust rules remain available.
- The assistant opens from a small button that uses the General chat mode icon.
- The assistant is a resizable right dock on desktop and a full-width overlay on small screens.
- Conversations persist as Email-scoped chats and expose new-chat/history controls.
- The assistant automatically receives lightweight context: active account, current Email view, and selected thread identifiers. Message bodies are fetched through fenced email tools only.
- The assistant uses a dedicated Email mode with email, calendar, web, file/document, Brain, utility, and question tools. It does not inherit unrelated shell, git, board, or settings capabilities.
- Digest actions initially apply to the active account rather than the unified inbox.

## Safety invariants

- Suggested digest actions are validated against the digest input message identifiers before they can be queued.
- AI-generated batch mutations never bypass the pending-action review queue unless the user has explicitly trusted the matching source/action rule.
- Sending mail always requires an explicit user action and continues through the existing undo-send outbox.
- Raw email HTML and bodies are not injected into the assistant prompt. The agent must use `get_thread` or search tools, which preserve untrusted-content fencing.
- File and document tools continue to use the chat workspace path and normal tool permission gates.

## Implementation outline

1. Reuse the existing digest action-group and pending-action renderers in the One Stream head, preserving current APIs and review-queue behavior.
2. Add missing semantic mail tools (`search_mail`, `get_thread`) to the email tool group.
3. Register a dedicated Email mode and work agent with the agreed tool groups and mail-specific safety instructions.
4. Add an Email assistant chat factory and app-scoped active-chat persistence without exposing Email chats in unrelated chat rails.
5. Mount the assistant dock inside the Email fullscreen app. Route the shared message renderer, composer surface, stream DOM, tool approvals, and question prompts into the dock while it is open.
6. Export a sanitized Email context snapshot and update it when account, view, or selected thread changes.
7. Extend Email panel resizing and responsive CSS for the assistant dock.
8. Add focused tests, update `documentation/context.md`, run Email tests and TypeScript checks, then verify the live UI and keyboard/focus behavior.

## Acceptance checks

- A digest with action groups displays actionable controls immediately below the narrative.
- Clicking a group creates one visible review item; Apply performs the action and Dismiss removes it.
- The General-icon button opens and closes the assistant without leaving Email.
- A conversation can be created, switched, reloaded, and resumed from Email.
- The assistant can search/read mail, draft replies, manage approved mail actions, inspect calendar data, browse the web, and create/read documents through normal permissions.
- The prompt knows the active account/view/thread identifiers but does not contain raw message bodies.
- The dock is keyboard accessible, returns focus on close, can be resized, and becomes a full-width overlay on narrow screens.
- Existing Email reader dock, virtual list, sync, and compose behavior remain functional.

## Shipped implementation

- One Stream renders validated digest suggestions as counted rows and shows pending mutations under **Ready for review**.
- Email chats persist with an app scope and dedicated Email mode, with New and History controls in the assistant header.
- The assistant dock reuses the shared transcript, composer, attachments, generation stream, tool approvals, and question UI.
- Account, view, folder, thread, subject, and message identifiers are sanitized and fenced in an ephemeral system message. Raw bodies and HTML are never injected.
- The dock is drag-resizable on desktop, becomes a full-surface overlay at the narrow breakpoint, restores focus when closed, and respects reduced motion.
- Focused Email, mode-policy, session, prompt-routing, server-validation, and TypeScript checks cover the implementation. Browser review covered dark and light themes plus desktop and narrow layouts, followed by a composer-density and compact-rail correction pass.
