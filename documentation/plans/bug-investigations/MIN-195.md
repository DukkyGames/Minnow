# MIN-195 Investigation

## Verification Status

**Reproduced by code path analysis — not runtime E2E in this session.**

The failure mode matches the implementation: after a wave completes in auto-pilot, the planner LLM is resumed and instructed to call `delegate_tasks`, but argument validation rejects common model shapes. Wave 2 tasks still start via the programmatic `autoDelegateNext()` path (“the other system”), which matches the bug report.

---

## Root Cause

**Dual, conflicting delegation paths in auto-pilot mode.**

Auto-pilot uses two mechanisms that are not coordinated:

| Path | Trigger | Mechanism |
|------|---------|-----------|
| **Programmatic (works)** | Task chat stream ends → `finalizeBoardTaskOnStreamEnd` → `moveTaskStatus('complete')` → `deliverOrchestratorTaskReport` → **`autoDelegateNext`** | `startTask()` directly, no LLM |
| **LLM-driven (fails)** | Same lifecycle report **resumes planner** via `resumeParentChatWithMessage` and tells it to call **`delegate_tasks`** | Tool call with `taskIds: string[]` |

The programmatic path is authoritative and usually succeeds. The LLM path is redundant but still prompted, and models frequently use the wrong argument shape after wave completion.

### Why the LLM call fails (“incorrect format”)

Validation is strict and does not normalize common mistakes:

1. **`validateToolRequiredArgs`** (`src/tools/validate-tool-required-args.ts`) — requires `taskIds` array; errors like:
   > `Error: tool "delegate_tasks" requires argument(s): "taskIds". Provide valid JSON in function.arguments (got { wave: W2 }).`

2. **`validateDelegateTasksArgs`** (`src/tools/board-tools.ts:388-404`) — requires `taskIds` or `task_ids` as a **non-empty array**; rejects:
   - `{ "wave": "W2" }` (prompt says “decide the next `delegate_tasks` **wave**”)
   - `{ "task_id": "W2-A" }` (confusion with `board_update_task`, which uses `task_id`)
   - `{ "taskIds": "W2-A" }` (string passes required-args check but fails array check)
   - `{ "tasks": ["W2-A"] }` (wrong key)

3. **Constrained tool parsing** (`src/tools/parse-tool-arguments.ts`) — malformed JSON yields:
   > `Tool arguments were not valid JSON.`

### Prompt / report amplification

- `buildOrchestratorTaskReportMessage` ends with: *“Call `delegate_tasks` to start the next ready planned tasks when Auto-pilot is on.”* (`src/agents/controller/report.ts:80`)
- `orchestrate.full.md` says: *“use them to decide the next `delegate_tasks` wave”* — wave-oriented wording encourages `wave` instead of `taskIds`.

### Supervisor / auto-resume

- Orchestrate **excludes** sub-agent completion push (`sub-agent-completion-push.ts:49`) — correct.
- Auto-pilot supervisor is `report.ts` + `autoDelegateNext`, not sub-agent resume.
- `deliverReport` skips resume when planner is streaming (`isChatStreaming`), but **`autoDelegateNext` still runs** after every `completed` report (`report.ts:154-156`). So Wave 2 can start programmatically while the planner is still processing an earlier report, then the LLM’s `delegate_tasks` hits already-started tasks (`status is in_progress, not planned`) or bad args.

## Proposed Fix

### Primary (recommended): Single source of truth — programmatic auto-pilot

1. **Stop prompting LLM to delegate after lifecycle events**
   - Remove `delegate_tasks` instruction from `buildOrchestratorTaskReportMessage`.
   - Update `orchestrate.full.md` / `orchestrate.lite.md`: auto-pilot delegation is automatic; planner only summarizes / handles failures.

2. **Optionally hide `delegate_tasks` from auto-pilot tool list**
   - In `orchestrate-tool-filter.ts`, always filter out `delegate_tasks` when `executionMode === 'auto'` (invert current logic), **or** keep tool for explicit re-delegation but document it as optional.

3. **Wave-complete batching (optional polish)**
   - Emit one planner notification per wave completion (not per task) to reduce resume churn and duplicate “Delegating Wave N” turns.

### Secondary (defense in depth): Harden `validateDelegateTasksArgs`

In `board-tools.ts`, before rejecting:

- Coerce `taskIds` string → `[string]` (comma-split).
- Accept `task_id` / `tasks` aliases.
- Accept `{ wave: "W2" }` → resolve to all **planned** tasks in that wave where `isTaskReadyForAuto(board, task)`.

Add tests for each alias and wave expansion.

### Tertiary: Race hardening

- Defer `resumeParentChatWithMessage` until wave is fully complete (all tasks in wave terminal), or coalesce pending reports.
- Ensure `deliverReport` skip does not leave planner unaware when `autoDelegateNext` already advanced the board (status-only report, no delegation instruction).
