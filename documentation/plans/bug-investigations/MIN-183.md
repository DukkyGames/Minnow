# MIN-183 Investigation

## MIN-183 — Context window does not update on previous chats

### Verification Status

**Confirmed (reproducible by code path analysis).**

The reported behavior matches the implementation:

| Scenario | `chat.modelInfo` | Context limit source | Updates after LM Studio change? |
|---|---|---|---|
| **New chat** | `{}` (empty) | Live `modelCache` → `loaded_context_length` | Yes (after `fetchModels`) |
| **Existing chat with prior turns** | `{ context_length: <old> }` persisted in session | Stale `chat.modelInfo.context_length` wins | No |
| **Existing chat after sending a message** | Overwritten at turn end via `resolveModelInfo()` | Fresh merge of cache + response | Yes (only after completion) |

Refresh plumbing is **not** the problem: `fetchModels()`, chat switch (`renderStatsForChat` / `renderChatFromHistory`), model select change, and `visibilitychange` all call `refreshContextUsageRing()`. The ring recomputes but reads the wrong limit for chats that already have `modelInfo.context_length` set.

---

### Root Cause

**Per-chat `modelInfo.context_length` is cached from the last completed turn and takes priority over the live model catalog when resolving the context window.**

`resolveContextLimit()` in `src/chat/context-usage.ts` uses this precedence:

1. `chat.modelInfo.context_length` (persisted per chat in `~/.minnow` sessions)
2. `contextLengthFromModelRow(cached)` from in-memory `modelCache` (refreshed by `fetchModels()` from LM Studio `GET /v0/models`)

That order was intentional for MIN-13 (reflect last-turn provider metadata), but it is wrong for **forward-looking** UI: the context ring and remaining-token estimate should reflect the **current** LM Studio configured window, not a snapshot from a prior send.

`chat.modelInfo` is written on every completed turn in `src/tools/loop.ts` and `src/api/chat.ts`, then persisted via `src/state/sessions.ts`. It survives app reload, so the stale value is durable.

A related display bug: `renderStatsForChat()` passes `chat.modelInfo` into `resolveModelInfo()`, and `resolveModelInfo()` merges `{ ...fromCache, ...fromResponse }`, so the stats strip `#iCtx` field also shows stale context on chat switch.

**Inconsistency:** sub-agent budget enforcement (`src/agents/sub-agent-runner.ts`) already uses live cache only (`contextLengthFromModelRow(cached)`), while main chat enforcement in `src/tools/loop.ts` calls `resolveContextLimit(sendModelId, chat)` — so main-chat context budgets can also be wrong on old chats.

### Proposed Fix

**Primary (required): invert precedence in `resolveContextLimit()`**

Use live catalog first; fall back to persisted `chat.modelInfo` only when cache is unavailable:

```ts
export function resolveContextLimit(modelId: string, chat: Chat): number | null {
  const cached = getModelRowForSelectOrCanonicalId(modelId);
  if (cached) {
    const fromRow = contextLengthFromModelRow(cached);
    if (fromRow != null) return fromRow;
  }

  const fromChat = chat.modelInfo?.context_length;
  if (typeof fromChat === 'number' && Number.isFinite(fromChat) && fromChat > 0) {
    return fromChat;
  }

  return null;
}
```

Rationale: context ring, remaining tokens, and `applyContextBudget()` in `loop.ts` are all **prospective** (next send). They should track current LM Studio `loaded_context_length`, not historical snapshots.

**Secondary (recommended): align stats strip on chat switch**

In `renderStatsForChat()` (`src/ui/messages.ts`), avoid passing full `chat.modelInfo` as the override for context display. Options:

- Call `resolveModelInfo(mid)` (live cache) for `#iCtx`, while still using `chat.lastStats` for turn metrics; or
- Add a small helper `resolveModelInfoForDisplay(modelId, chat)` that prefers cache for `context_length` but keeps persisted `arch`/`quant` if desired.

**Optional hardening**

- After `fetchModels()`, if `chat.modelInfo.context_length` differs from `contextLengthFromModelRow(cached)` for matching `modelId`, clear or update the field (session write). Belt-and-suspenders if other call sites still read `chat.modelInfo.context_length` directly.
- On `visibilitychange`, call `fetchModels()` (not only `refreshContextUsageRing()`) so cache stays fresh when LM Studio is changed while Minnow is backgrounded. Separate enhancement; not required if precedence fix lands.

**Docs / tests**

- Update `test/chat/context-usage.test.mts` — cache should win when both cache and `chat.modelInfo` are present and differ.
- Update `documentation/context.md` MIN-13 precedence note.

**Out of scope for this bug:** `agent-activity-panel.ts` has its own `contextCache` for activity rows; unrelated to composer ring.
