## MIN-184 — Random Chat Errors

### Verification Status

**Confirmed by static code analysis** (not reproduced live in this session — no LM Studio instance available). The reported symptoms match the implementation:

| Symptom | Matches code? |
|--------|----------------|

### Root Cause

**Failed generations persist a partial tool-loop transcript to `chat.history` without rollback or outbound sanitization. Subsequent sends replay that transcript to the provider, which returns HTTP 500 (often as an HTML error page from LM Studio / llama.cpp).**

Three gaps combine:

1. **No rollback on failed turns** — When generation fails, the catch block shows a DOM-only error bubble but does not revert history. Partial assistant + tool rows from the failed run remain in `chat.history` and are saved to disk.

2. **No outbound tool-message sanitization** — `buildApiMessages()` serializes `chat.history` as-is. `normalizeHistoryTail()` exists for truncate/fork flows but is **not** called on the outbound API path. There is no equivalent of Odysseus’s `_sanitize_tool_messages` (drop orphan `tool` rows, strip dangling `tool_calls`).

3. **Removed post-tool-tail recovery** — Phase 3 removed `turn-recovery.ts` orphan tool-tail auto-retry. `hasPostToolTail()` still detects the condition but is only used for empty-response retries inside the same turn, not for failed-turn recovery or reprompt.

**Why new chats work:** Fresh `chat.history` has no poisoned tool tail.

**Why reprompt fails repeatedly:** Each new user message is appended on top of the corrupted history; `buildApiMessages` replays the full chain every time.

### Proposed Fix

**Do not implement in this ticket — recommended approach (ordered by impact):**

#### A. Roll back failed run output (primary fix)

In `runChatTurn` catch when `turnRunStatus === 'failed'`:

- If `run.outputHistoryStart` is defined, splice `chat.history` back to `forkHistoryIndex` (keep the user message; drop partial assistant/tool rows from the failed attempt).
- Re-render chat from history (`renderChatFromHistory`) so the error bubble is replaced by a clean transcript.
- Optionally persist a lightweight `lastTurnError` on the chat for UI display instead of leaving a dead error bubble.

#### B. Sanitize outbound messages before upstream (defense in depth)

Add `sanitizeOutboundToolMessages(messages: ApiMessage[]): ApiMessage[]` (port logic from Odysseus `context_compactor._sanitize_tool_messages`):

- Drop orphan `role: tool` messages with no preceding `tool_calls`.
- Strip dangling `tool_calls` from assistant messages with no following tool results.
- Call from `buildApiMessages` return path (on a copy, not mutating session history).

Also call `normalizeHistoryTail` on the session-history copy used for API build when detecting incomplete chains.

#### C. Restore post-tool-tail recovery on send

Before `buildApiMessages` in the tool loop:

- If `hasPostToolTail(chat.history)` and this is a **new** user send (not mid-loop continuation), either:
  - Auto-inject `EMPTY_POST_TOOL_CONTINUE_INSTRUCTION` as ephemeral user line (already defined in `turn-continuation.ts`), **or**
  - Roll back to last complete assistant reply and treat as resend.

This replaces the removed `turn-recovery.ts` behavior.

#### D. Harden tool-loop execution

Wrap the per-tool `executeTool` loop in `try/finally` so every `tool_call.id` gets a `role: tool` result (synthetic `Error: tool execution interrupted` on throw), preventing incomplete chains.

#### E. UX: Retry affordance on error bubble

Add a **Retry** action on the error bubble that calls `resendFromIndex(chatId, forkHistoryIndex)` (existing `fork-from-run.ts`) instead of requiring the user to send a new message atop poisoned history.
