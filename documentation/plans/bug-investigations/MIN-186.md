# MIN-186 Investigation

## MIN-186 — Switching editor tabs triggers unsaved-changes popup

### Verification Status

**Confirmed false positive** (code analysis; no reproduction run in this session).

The unsaved-changes dialog (`"You have unsaved changes. Continue without saving?"`) can appear when switching between editor tabs even though the user made no edits. The tab strip may also show a dirty marker (●) incorrectly.

Relevant flow:

1. Tab click → `activateTabAndRender` → `confirmLeaveDirtyActiveTab`
2. File tree / go-to-definition → `openFileInViewer` → `openViewerTab` → same confirm callback
3. Dirty state: `text !== tab.originalContent` in `snapshotActiveTabFromEditor` and the CodeMirror `updateListener`

---

### Root Cause

Three interacting bugs in `src/ui/file-viewer.ts` and `src/ui/file-viewer-tab-store.ts`:

#### 1. `destroyEditor()` snapshots against the wrong tab (primary)

On every tab switch, `activateViewerTab` sets the **new** tab active **before** `renderActiveViewerTab` → `mountEditor` → `destroyEditor`. `destroyEditor` always calls `snapshotActiveTabFromEditor()`, which reads `getActiveViewerTab()` (already the **destination** tab) but `editorView` still holds the **outgoing** tab’s buffer.

That writes the outgoing file’s text into the incoming tab’s `cachedEditorContent` and sets `isDirty = (outgoingText !== incomingOriginal)`, which is almost always `true` for different files.

#### 2. Async `mountEditor` race (secondary / intermittent)

`mountEditor` creates the CodeMirror view inside an unguarded `async` IIFE. A slow in-flight mount from tab A can finish after the user has switched to tab B and assign `editorView` to the wrong document. Subsequent snapshots then compare the wrong buffer to `originalContent`, leaving `isDirty === true` or skipping snapshot when `editorView` is `null` during the async gap.

#### 3. Inconsistent snapshot before unsaved guard (tertiary)

Tab-strip clicks call `snapshotActiveTabFromEditor()` **before** the confirm dialog (`activateTabAndRender`). File-tree navigation via `openFileInViewer` / `openViewerTab` does **not**, so a falsely dirty tab from (1) or (2) triggers the popup when switching via the tree even if a tab-strip switch would have self-corrected.

**Repro sketch (no edits)**

1. Open `fileA.ts` and `fileB.ts` in the viewer.
2. Switch A → B via tab strip (or open B from tree while A is active).
3. `destroyEditor` marks B dirty with A’s buffer.
4. Switch B → A (or click another file in the tree).
5. Confirm dialog appears; B may show ● in the tab strip.

Worse if step 2–4 happen during CodeMirror’s async extension load (`editorView === null` → snapshot skipped → stale `isDirty` persists).

### Proposed Fix

**Do not implement in this ticket — design only.**

1. **Track editor ownership**  
   Add `editorViewPath: string | null`, set when creating `editorView`, cleared in `destroyEditor`. In `snapshotActiveTabFromEditor`, return early unless `editorViewPath === tab.path`.

2. **Fix teardown snapshot**  
   Either:
   - Remove `snapshotActiveTabFromEditor()` from `destroyEditor` and require callers to snapshot **before** changing the active tab, or  
   - Pass the outgoing tab path explicitly into `destroyEditor({ snapshotPath })`.

3. **Mount generation token**  
   Increment a counter at the start of `mountEditor`; only assign `editorView` if the token still matches when the async block completes. Discard stale mounts.

4. **Unify navigation paths**  
   Call `snapshotActiveTabFromEditor()` (or a shared `prepareToLeaveActiveTab()`) at the start of `openViewerTab` before `confirmUnsaved`, matching `activateTabAndRender`.

5. **Optional hardening**  
   In the `updateListener`, compare against `getViewerTab(path)` by path key instead of a closed-over `tab` reference, so stale listeners cannot mutate the wrong tab.
