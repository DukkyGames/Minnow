# MIN-187 Investigation

## MIN-187 — Reloading mid chat

**Linear:** [MIN-187](https://linear.app/minnowai/issue/MIN-187/reloading-mid-chat)  
**GitHub:** [#253](https://github.com/DukkyGames/Minnow/issues/253)

---

### Verification Status

**Confirmed (static code analysis)** — root cause is reproducible from the boot-resume + tool-loop interaction. Not live-reproduced in this pass, but the failure mode is deterministic whenever:

1. A chat has a persisted `currentGenerationId` after reload, and  
2. Boot resume re-subscribes to a generation whose replayed stream ends with `tool_calls`.

---

### Root Cause

**`resumeGenerationId` is reused for every tool-loop round, not just the first.**

After reload, `bootGenerationResumeForChat` calls `runChatTurn` with `resumeGenerationId` set to the persisted `chat.currentGenerationId`. Inside the tool loop, that same ID is passed into `streamCompletionTurn` on **every** iteration:

```1296:1301:src/tools/loop.ts
      const runStreamTurn = (turnBody: ChatCompletionBody) =>
        streamCompletionTurn(
          chat,
          provider,
          turnBody,
          resumeGenerationId,
```

`streamCompletionTurn` treats a non-empty `resumeGenerationId` as subscribe-only (skips `POST /api/generations`). The server replays the **full buffered stream from zero** on each subscribe (`addSubscriber` in `server/generations/store.js`), then emits `event: end`.

**Failure sequence:**

1. Reload mid-stream → boot resume subscribes to generation `G` and replays it.  
2. Replay yields `tool_calls` → tools execute → history grows → loop continues.  
3. Round 2+ still passes `resumeGenerationId = G` → **same completed generation is replayed again** → same `tool_calls` re-dispatched → tools re-execute.  
4. Repeats until `maxToolTurns` (default **100** in `src/config/chat-meta.ts`).

`streamCompletionTurn` clears `chat.currentGenerationId` after a successful subscribe (line 709), but the **closure variable** `resumeGenerationId` in `runChatTurn` is never cleared, so subsequent rounds keep re-subscribing.

**Contributing factors:**

| Factor | Effect |
|--------|--------|
| `clearStaleGenerationIdsOnLoad` only drops IDs when the last message is a non-empty `assistant` prose row | Correct for mid-stream resume, but IDs survive when history ends with `tool` or `assistant` + `tool_calls` — expected, yet amplifies duplicate execution when combined with the bug |
| Boot resume skips turn snapshot creation (`if (!resumeGenerationId)` at line 1135) | Resume path has weaker run/trace bookkeeping; not the loop driver, but harder to debug |
| No idempotency on tool execution after replay | Replayed `tool_call_id`s are not checked against history before `executeTool` |

**Not the primary cause:** orchestrate `resumeParentChatWithMessage` / sub-agent completion push — those start fresh turns without `resumeGenerationId`.

### Proposed Fix

#### 1. Primary — one-shot `resumeGenerationId` (required)

In `runChatTurn`, treat boot resume as single-use:

```typescript
let activeResumeGenerationId = resumeGenerationId;
// pass activeResumeGenerationId into streamCompletionTurn
// after first successful streamCompletionTurn:
activeResumeGenerationId = undefined;
```

Or only pass `resumeGenerationId` when `turn === 0`.

Subsequent tool-loop rounds must call `createGeneration` (normal POST path).

**Scope:** ~5–15 lines in `src/tools/loop.ts`.

#### 2. Secondary — idempotent tool execution on resume (recommended)

Before executing tools from a replayed stream, skip any `tool_call_id` already present in `chat.history` (assistant `tool_calls` or `tool` rows). Prevents duplicate side effects if history was partially persisted before reload.

#### 3. Tertiary — stale generation hygiene (optional)

Extend `clearStaleGenerationIdsOnLoad` to drop `currentGenerationId` when history already contains the assistant `tool_calls` message matching the in-flight generation’s outcome (harder without server metadata; client-only heuristic: if last message is `tool` and no `currentGenerationId` subscriber is active, clear on failed resume).

#### 4. Tests (required with fix)

- Unit: mock `createGeneration` / `subscribeToGeneration` — after resume round 1 with `tool_calls`, round 2 must call `createGeneration`, not subscribe.  
- Unit: reload-resume when replayed stream has `tool_calls` already in history → tools not re-executed.  
- Regression: resume of prose-only stream still works (single round, no POST on round 2 because loop exits).

**Out of scope for MIN-187:** full checkpoint of tool-loop phase (`streaming` vs `executing-tools` vs `post-tool-synthesis`) — larger feature; one-shot resume fixes the reported infinite loop.

### Test Plan

1. **Repro (manual):** Build mode chat with tools enabled; send a prompt that triggers tool calls; reload while the assistant stream is active (spinner / thinking dot); confirm tools run once and the turn completes with prose.  
2. **Repro (manual):** Multi-tool round trip (tool → synthesis stream → reload mid second stream with tools again); confirm no repeated identical tool cards.  
3. **Automated:** New test in `test/chat/generation-resume.test.mts` or `test/tools/loop-resume.test.mts` asserting subscribe called once per boot resume.  
4. **Automated:** Assert `createGeneration` called for post-tool round after resume.  
5. **Regression:** Existing `generation-resume.test.mts` 404 test still passes.  
6. **Regression:** Normal send (no reload) tool loop unchanged.  
7. **Edge:** Reload during tool execution (after stream ended, `currentGenerationId` cleared) — chat should **not** auto-resume; user can continue manually (document expected behavior).
