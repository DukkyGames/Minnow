# MIN-194 Investigation

## MIN-194 — Can not open chats when in board view

### Verification Status

**Confirmed (code analysis).** Reproduces across three related entry points:

| Issue | Scenario | Expected | Actual (per code + reports) |
|-------|----------|----------|-----------------------------|
| **MIN-194** | Any chat open while board is visible | Main column shows chat transcript | Board DOM stays in `#chatArea` |
| **MIN-193** | Click orchestrator activity chip / header message | Open planner chat view | Composer un-hides; board kanban remains |
| **MIN-182** | Switch to chat **outside** board folder | Leave board, show target chat | Board stays; workaround: open in-folder chat first |

No automated test covers `switchChat` while `activeBoardGroupId` is set. Existing board tests (`test/ui/view-mode-toggle.test.mjs`) use legacy `chat.viewMode` and do not exercise the v5 `ChatGroup` + `activeBoardGroupId` flow.

---

### Root Cause

**Primary:** `switchChat` returns early when `id === sessionState.activeId` **before** any board teardown or DOM refresh.

When board view opens, `openBoardGroup` sets `activeId` to the planner chat:

```177:197:src/state/chat-groups.ts
export function openBoardGroup(groupId: string): void {
  // ...
  if (plannerId && active && active.id !== plannerId && ...) {
    state.activeId = plannerId;
  }
  state.activeBoardGroupId = groupId;
  group.viewMode = 'board';
```

So while the board is open, the planner is usually already active. Any “open chat” action that targets the planner hits:

```672:675:src/ui/sidebar.ts
  if (!sessionState || id === sessionState.activeId) {
    closeMobileSidebar();
    applySidebarVisuals();
    return;
  }
```

`renderChatFromHistory` is never called → `.board-root` stays mounted.

**MIN-193 path:** Activity chip calls `setOrchestrateViewMode('chat')` → `closeBoardGroupView` → `switchChat(plannerId)`. State is cleared (`viewMode = 'chat'`, `activeBoardGroupId` deleted), but `switchChat` early-returns because planner is already active. `syncBoardViewChrome()` removes `main-column--board-view` (composer shows) while board DOM remains — matches the report.

**Secondary (MIN-182):** Board exit in `switchChat` only resets `viewMode` on the **destination** chat’s group, not the **currently open** board folder:

```686:691:src/ui/sidebar.ts
  if (sessionState.activeBoardGroupId) {
    delete sessionState.activeBoardGroupId;
    const boardGroup = sessionState.groups?.find(
      (g) => g.id === chat.boardGroupId || g.id === chat.groupId,
    );
    if (boardGroup) boardGroup.viewMode = 'chat';
  }
```

Switching to an out-of-folder chat clears `activeBoardGroupId` but leaves the open folder at `viewMode: 'board'`. That matches the reported workaround (switch to an in-folder chat first — that path resets `viewMode`). There is also no call to `disposeBoardSession()` or `syncOrchestrateInitSplitChrome()` on exit, so board subscriptions / init-split layout can linger.

**Guard that re-paints board:** `renderChatFromHistory` short-circuits to board when board mode is active:

```158:165:src/ui/messages.ts

  if (boardGroup?.viewMode === 'board') {
    teardownHub();
    void import('./orchestrate-board').then((m) => {
      m.renderBoardView(boardGroup);
```

This is correct while board is open, but anything that clears state without forcing a chat re-render leaves stale board DOM.

### Proposed Fix

**Do not implement yet** — recommended minimal, unified approach:

#### 1. Add `exitBoardViewForNavigation()` (e.g. in `src/state/chat-groups.ts`)

- Capture open group via `getActiveBoardGroup()` before mutations
- Set `group.viewMode = 'chat'`, delete `activeBoardGroupId`
- Call `disposeBoardSession()` (export from `orchestrate-board.ts` or wrap `disposeBoardViewForTests` logic)
- Call `syncOrchestrateInitSplitChrome()` to tear down init-split panes
- Return whether board was active (for forced re-render)

#### 2. Fix `switchChat` (`src/ui/sidebar.ts`)

- Call `exitBoardViewForNavigation()` **before** the same-id check (or pass a `forceRender` flag)
- When exiting board, reset the **open** group’s `viewMode`, not only the destination’s
- If `id === activeId` **but** board was just exited → still call `renderChatFromHistory(chat)`, `syncViewModeToggleFromActiveChat()`, `renderSidebar()`

#### 3. Fix `closeBoardGroupView` (`src/state/chat-groups.ts`)

- After state cleanup, if `state.activeId === plannerId` → call `renderChatFromHistory(planner)` directly instead of `switchChat(plannerId)`
- Avoid async `import('./sidebar')` for the common planner-already-active case

#### 4. Optional hardening

- Sidebar chat click while board open: always route through shared exit helper
- `openBoardTaskChat` / task-card `switchChat` already go through `switchChat`; they benefit from (2) when switching to task chat with planner still active only if task id differs (already works); planner same-id cases need (2)+(3)
