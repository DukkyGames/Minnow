# MIN-191 Investigation

## MIN-191 — Mode switch: `set_chat_mode` sometimes fails with "Finish current reply first"

### Verification Status

**Confirmed (code-level, high confidence).** The error string is exact: `'Finish the current reply first'` in `setChatMode()`. The failure is **deterministic** whenever `set_chat_mode` runs while the active chat is in an in-flight turn. It appears **intermittent** only because some handoff paths avoid that window.

| Path | During streaming? | Result |
|------|-------------------|--------|
| `propose_mode_switch` → user answers → `set_chat_mode` (same turn) | Yes | **Fails** |
| User sends new message → model calls `set_chat_mode` (new turn) | No (at tool call) | **Works** |
| `create_chat_with_mode` (new chat) | N/A — no mode change on streaming chat | **Works** |
| Manual mode segment click | Yes (buttons disabled) | Blocked by design |

---

### Root Cause

**Architectural mismatch:** `set_chat_mode` is meant to run **inside** the tool loop after handoff, but `setChatMode()` uses the same guard as **manual UI** actions and blocks while streaming.

1. **`set_chat_mode` → `executeSetChatMode()` → `setChatMode()`** (`src/tools/mode-handoff-tools.ts`, `src/ui/mode-selector.ts`).

2. **`setChatMode()` rejects when `isActiveChatStreaming()` is true** (lines 96–97 in `mode-selector.ts`).

3. **Streaming spans the entire multi-round tool turn**, not just token SSE:
   - `setStreaming(true, chat.id)` at turn start (`src/tools/loop.ts` ~995)
   - Tools run while flag is still set (~1409–1480)
   - `setStreaming(false, chat.id)` only in `finally` when the turn fully ends (~1907)

4. **Prompts instruct the failing sequence.** Example from `plan.full.md`: after `propose_mode_switch` with `plan_complete`, on “Implement in Build” → call `set_chat_mode` with `build` — typically **same turn**, while streaming.

5. **`propose_mode_switch` is not blocked** — it uses `enqueueAskQuestion()` with no streaming check. Only the follow-up `set_chat_mode` fails.

6. **Why the guard exists:** `setChatMode()` calls `renderChatFromHistory()`, which can tear down streaming DOM (hub/board swap, `area.innerHTML = ''`). Blocking mid-stream for **UI clicks** is correct; blocking **programmatic handoff tools** is not.

### Proposed Fix

**Recommended: defer programmatic mode switch until stream end** (mirror `pendingSteerMessage` in `src/chat/steer-message.ts`).

#### 1. Add deferred state on `Chat`

```ts
pendingModeId?: ModeId;  // last-write-wins; cleared on apply or explicit cancel
```

#### 2. Split guard behavior by source

- **UI** (`selectMode`, keyboard nav): keep current block; segments stay disabled via `refreshModeSelectorDisabled()`.
- **Tool** (`executeSetChatMode`): if `isActiveChatStreaming()`:
  - set `chat.pendingModeId = modeId`, persist
  - return `JSON.stringify({ ok: true, deferred: true, modeId, label })` so the model knows it succeeded
- If not streaming: existing `setChatMode` behavior unchanged.

#### 3. Flush on stream end

In `notifyChatStreamEnd` subscriber or `runChatTurn` `finally` (after `setStreaming(false)`):

```ts
if (chat.pendingModeId) {
  const mode = chat.pendingModeId;
  chat.pendingModeId = undefined;
  setChatMode(mode);  // safe — streaming now false
}
```

Also flush on **user stop** so a chosen handoff is not lost.

#### 4. Optional hardening

- `setChatMode(modeId, { source: 'ui' | 'tool' })` to make intent explicit.
- If `chat.modeId === modeId` when deferring, no-op with `{ ok: true }`.
- Log/metric when deferral happens (debugging).

#### Alternatives (not recommended)

| Approach | Issue |
|----------|--------|
| Remove streaming guard entirely | `renderChatFromHistory()` mid-stream breaks live assistant DOM |
| Update `chat.modeId` only, skip render | Mode selector/orchestrate chrome out of sync; board/hub transition unsafe |
| Prompt-only: “wait for next turn” | Unreliable; fights documented handoff flow |

### Test Plan

1. **Unit — defer during streaming**  
   Set `setStreaming(true, chatId)`, call `executeSetChatMode({ mode_id: 'build' })`, assert `deferred: true`, `chat.pendingModeId === 'build'`, `chat.modeId` unchanged.

2. **Unit — flush on stream end**  
   Queue `pendingModeId`, call `setStreaming(false)`, run flush, assert `chat.modeId === 'build'` and pending cleared.

3. **Unit — UI guard unchanged**  
   With streaming on, `setChatMode('build')` from UI path still returns `{ ok: false, error: 'Finish the current reply first' }`; mode segments disabled.

4. **Integration — handoff happy path**  
   Simulate: `propose_mode_switch` → mocked answer → `set_chat_mode` in same synthetic turn; assert deferred then applied at turn end.

5. **Regression — `create_chat_with_mode`**  
   Still succeeds during streaming on source chat.

6. **Regression — stop behavior**  
   Deferred mode still applies (or is explicitly cancelled) when user stops generation.

7. **Manual QA**  
   Plan mode → finish plan → `propose_mode_switch` → “Implement in Build” → mode switches to Build without tool error; hub/board layout correct after stream ends.

**Summary:** MIN-191 is a real bug, not a flaky race. The documented `propose_mode_switch` → `set_chat_mode` flow runs inside a streaming turn and always hits the UI-oriented guard. Defer application until stream end preserves DOM safety and fixes the handoff tool reliably.
